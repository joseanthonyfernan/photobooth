SQL Injection: Vulnerabilities and Prevention

1. The Vulnerable Approach (Direct Concatenation)

In login_vulnerable.php, user input is directly concatenated into the SQL query string. This is highly dangerous because the database engine cannot distinguish between the developer's intended SQL structure and the data provided by the user. The data is treated as executable code.

Example Attack: If an attacker enters ' OR '1'='1' -- as the username, the resulting query becomes:

SELECT * FROM users WHERE username = '' OR '1'='1' -- ' AND password = '...'

Because '1'='1' is a condition that is always true, the database returns a valid row (often the first user in the table, typically an administrator). The -- instructs MySQL to treat the rest of the query as a comment, meaning the password check is entirely ignored. The attacker has successfully bypassed authentication without knowing any passwords.

Code Implementation (Vulnerable)

// 1. Inputs are taken directly from the user
$username = $_POST['username'];
$password = hash('sha256', $_POST['password']);

// 2. The inputs are concatenated directly into the SQL string
$sql = "SELECT * FROM users WHERE username = '$username' AND password = '$password'";

// 3. The query is executed as-is
$result = $conn->query($sql);

Explanation: In the code above, the variables $username and $password are inserted directly into the query string using string interpolation. If the user types SQL commands (like single quotes ' or comments --) into the input fields, the database will interpret those commands as part of the query logic instead of just plain text data.

2. The Secure Approach (Prepared Statements)

In login_secure.php, we use Prepared Statements (parameterized queries) to eliminate this vulnerability.

A prepared statement separates the SQL code structure from the user-provided data. The SQL statement template is sent to the database server first and compiled. Then, the user inputs are sent separately as bound parameters.

Why it prevents SQLi: Because the structure is already compiled, the database engine treats the bound parameters strictly as literal values (data), never as executable SQL code. If an attacker inputs ' OR '1'='1' -- , the database simply searches for a user whose literal username is exactly that string. It does not execute the OR clause, completely neutralizing the injection attempt.

Code Implementation (Secure)

// 1. Inputs are received
$username = $_POST['username'];
$password = hash('sha256', $_POST['password']);

// 2. The SQL statement is PREPARED using placeholders (?)
$stmt = $conn->prepare("SELECT id, username, password FROM users WHERE username = ? AND password = ?");

// 3. The user inputs are BOUND to the placeholders strictly as strings ("ss")
$stmt->bind_param("ss", $username, $password);

// 4. The statement is executed safely
$stmt->execute();

Explanation: Here, the SQL statement is defined with ? placeholders. The prepare() function sends this empty structure to the database first. When bind_param() is called, the database receives the user inputs completely separately. It explicitly treats the inputs as literal strings (denoted by "ss"). Even if the user inputs SQL commands, the database ignores them because it has already locked in the query structure.

3. Proper Input Validation and Sanitization

While prepared statements prevent SQL injection, comprehensive web security requires a "Defense in Depth" strategy. In register.php and login_secure.php, we implemented robust validation and sanitization:

  • Validation: Ensures that data conforms to strict expected formats before any processing occurs. For example, verifying a username is exactly 5-20 alphanumeric characters using Regular Expressions (preg_match), or ensuring an email is structurally valid (filter_var). Validation acts as a gatekeeper, rejecting malicious or malformed input immediately.
  • Sanitization: Removes or safely encodes potentially dangerous characters. For example, using htmlspecialchars() or strip_tags() prevents Cross-Site Scripting (XSS) attacks. This ensures that if the user's input is later displayed on a webpage, it renders as harmless text rather than executing malicious JavaScript in another user's browser.

Conclusion: Security must be proactive. Combining input validation (to ensure data correctness), sanitization (to prevent XSS), and prepared statements (to prevent SQLi) ensures that an application is resilient against the most common and dangerous web vulnerabilities.
